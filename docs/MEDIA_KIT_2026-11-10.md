# Редакционный пакет открытой беты: 1C BSL AI Copilot

Черновик для редактора, разработчика 1С и владельца релиза. **Не публиковать до проверки точной опубликованной версии и live canary NormaHub.** Сводный release gate и каналы: [RELEASE_AND_GROWTH_2026-11-10.md](RELEASE_AND_GROWTH_2026-11-10.md).

## Позиционирование и факты

**Кому:** разработчику 1С, который редактирует BSL в VS Code или Cursor и хочет быстрее получать черновик запроса, локальные замечания и безопасно просматривать предложенные правки. **Что делает:** показывает AI-черновик, preview, позволяет копировать/открыть отдельно/применить к исходному документу; локальные проверки и шаблоны работают без NormaHub key. **Чего не делает:** не сертифицирует код на соответствие всем стандартам, не гарантирует бизнес-корректность, не создаёт готовый `.cfe`, не заменяет запуск в 1С.

Для первого экрана любого материала: «Открытая бета расширения для разработки BSL в VS Code/Cursor. AI-ответ — черновик, который разработчик проверяет перед применением. Облачные задачи используют NormaHub API и оплачиваются по действующим условиям сервиса; локальные инструменты доступны без ключа».

Допустимо только после проверки опубликованного VSIX: «Устанавливается из [проверенная ссылка] и активируется в [точные версии IDE]». Не писать: «проверяет весь BSL», «AI гарантирует корректный запрос», «готов для любого ERP/УПП», «мгновенно дополняет код», «готовая обработка 1С», «конкурентам нет равных». Числа прошлых испытаний указывать с датой, N и стендом, если вообще нужны для технической статьи.

## Что подготовить один раз

1. Точный tag, SHA опубликованного VSIX, ссылки на GitHub/Marketplace/Open VSX после фактической публикации; один stable URL quick start и один URL поддержки. Если реестры ещё не синхронизированы, текст остаётся черновиком.
2. Один собственный demo-проект/BSL без коммерческих или пользовательских данных. На видео показать исходное требование, реальные имена схемы, ответ, preview, ручную проверку/применение и, если заявляется, выполнение выбранного запроса в учебной 1С. Отдельная заставка «тестовая конфигурация».
3. Скриншоты: панель RU, генерация и preview, защита от устаревшего документа, локальная проверка без ключа, настройка подключения, EN. Каждый кадр должен быть снят **с опубликованной версии**, содержать читаемый результат и не показывать ключи/баланс/личные пути.
4. Открытая политика данных в коротком виде: какой фрагмент кода/метаданных идёт в NormaHub, что остаётся локально, где отключить AI, где фактические условия использования и оплаты. Проверить с владельцем gateway до релиза.
5. FAQ: «Нужен ли ключ?», «Что бесплатно?», «Куда уходит код?», «Работает ли в Конфигураторе?», «Есть ли готовые .cfe/.epf?», «Почему предложение может быть медленным?», «Какие версии IDE/1С проверены?», «Куда сообщить об ошибке без раскрытия проекта?».

## Материал 1 — короткий анонс в собственных каналах

**Когда:** после проверки Marketplace/Open VSX и установки из каждого канала. **Где:** блог NormaHub, собственный Telegram/VK, страница GitHub Release. Это контролируемые каналы; один URL с UTM на установку.

**Рабочий заголовок:** «Открытая бета 1C BSL AI Copilot: черновик запроса и проверяемое применение в VS Code/Cursor».

**Структура 120–180 слов:** (1) проблема: черновик легко получить, но важно не вставить его в не тот модуль; (2) один экранный сценарий: BSL → описание → AI-черновик → preview → ручная проверка; (3) локальные инструменты без ключа и отдельная стоимость облачных запросов; (4) пределы беты, особенно скорость inline и неподтверждённые конфигурации; (5) две ссылки: установка и помощь. Не писать про «полноценную интеграцию в 1С», если речь о редакторе.

**Медиа:** 30–45 секунд без монтажа результата из разных версий. Первый кадр — исходный BSL/требование; финальный — применённый код в том же документе или обоснованный отказ. Звук необязателен; русские субтитры обязательны для короткого ролика.

## Материал 2 — Инфостарт: практическая инструкция, не рекламный пресс-релиз

**Рабочий заголовок:** «Черновик запроса 1С из описания в VS Code: как проверить результат перед применением».

**Порядок внутри статьи:** задача и версия тестовой платформы → исходная схема и требование → установка/точные требования → ввод в расширении → screenshot preview → ручная сверка имён/параметров → выполнение выбранного SELECT на собственном тестовом стенде → ошибки и неподдерживаемые случаи → где взять исходник/пакет **если формат ссылки/вложения согласован** → условия облачного использования.

**В редакторе площадки:** профиль → «Создать публикацию» → сохранить черновик → заголовок, анонс, описание, квадратная/горизонтальная обложка ≥300×300, галерея в разделе «Изображения», корректный вид объекта/рубрики/версии, файл программы и свойства вложения по правилам. При использовании сторонних картинок загрузить их в «Изображения», не вставлять как внешний `img`. До отправки на модерацию вычитать текст предметным специалистом.

**Ограничения:** [правила Инфостарта](https://infostart.ru/about/rules/publishing_rules/) ограничивают прямые контакты и внешние ссылки, коммерческие публикации вне механизма площадки, требуют открытый исходник у бесплатной разработки и запрещают непроверенные AI-тексты. Поскольку VSIX MIT, а облачный gateway платный, согласовать у модератора категорию и допустимость модели распространения до загрузки; не маскировать платные запросы словом «бесплатно». [Справка по оформлению](https://infostart.ru/about/help/28158/683216/).

## Материал 3 — Habr: инженерный разбор

**Рабочий заголовок:** «Как мы защищаем BSL-модуль от применения устаревшего AI-ответа».

**Структура:** (1) конкретный race: смена вкладки/версии документа во время генерации; (2) URI + версия + позиция + identity запроса; (3) preview и once-only apply; (4) отрицательные случаи: close/reopen, stale response, отмена, Undo; (5) что показал installed IDE тест, а что проверялся только с контролируемым transport; (6) границы живой 1С и latency; (7) итоговый технический trade-off. Дать фрагменты собственного кода и воспроизводимую методику, не рекламу и не сравнение с конкурентом без benchmark.

**Размещение:** техническая статья в подходящем хабе при соблюдении [правил Хабра](https://habr.com/ru/docs/help/rules/). Если основная цель — продвижение продукта и ссылка на установку, использовать разрешённый корпоративный блог или формат «Я пиарюсь»; личный профиль нельзя превращать в рекламный канал. Редактор проверяет ссылочную политику перед публикацией.

## Материал 4 — видео и англоязычный запуск

**Видео 3–5 минут для YouTube/RuTube/VK Video:** 0:00 проблема и конкретный BSL; 0:20 установка из каталога; 0:50 локальный сценарий без ключа; 1:30 настройка API и предупреждение о передаче данных/цене; 2:00 генерация на настоящем вызове; 2:50 preview и проверка; 3:30 отказ или apply/Undo; 4:00 ограничения и ссылка поддержки. Если live вызов не удаётся, не подменять его записью из фикстуры без явной пометки «replay».

**Product Hunt — отдельный англоязычный день, не первый приоритет РФ 1С:** проверить EN quick start, install links и демонстрацию, подготовить launch name/tagline/description/logo/gallery/tags/maker role, ответственного на комментарии. Собственный продукт может публиковать maker; [официальный список полей](https://help.producthunt.com/en/articles/17834537-4-build-your-product-page). Пояснять, что BSL относится к 1C:Enterprise, а не к C#; не обещать международную совместимость всех конфигураций.

**MCP Registry/Glama:** только после отдельного реально устанавливаемого MCP-пакета. Статья о девяти локальных tools должна содержать exact install/initialize/list/call, показывать, что эти tools сами не вызывают облачный AI, и не подменять их возможностями VSIX.

## Раскладка каналов и измерение

**T0:** GitHub, Marketplace, Open VSX, собственный анонс. **T+2…7:** Инфостарт черновик/модерация, ответы на Issues. **T+5…14:** инженерный Habr материал и видео. **T+21…45:** разбор отказов, обновлённое demo, образовательный вебинар. Product Hunt, MCP Registry и Glama — отдельные запуски после их собственных gates.

UTM по каналам ведёт на собственную страницу установки; она не собирает BSL-код. Отслеживать click→install→first BSL open→first local result→key configured→first useful AI result→repeat use; сообщать знаменатели. Не покупать широкие размещения до живого корпуса 30/30 и оценки стоимости полезного результата. Возможные большие вложения — обучение партнёров, интеграторы, отдельная Windows-линия, независимый benchmark — только после подтверждения узкого сценария и его экономики.

**Финальная редакционная проверка перед отправкой:** версия/ссылка/цена/конфигурация/платформа верны; кадры из текущего релиза; demo не раскрывает ключи или чужой код; сильные слова имеют evidence; ограничения и способ получить помощь видны без прокрутки до конца.
