# Релиз и рост 1C BSL AI Copilot: решение CEO и рабочий runbook

Срез: 2026-11-10. Продукт — расширение для VS Code/Cursor с локальными инструментами, облачными AI-сценариями через NormaHub, локальным stdio MCP и экспериментальными адаптерами. Релиз расширения, релиз отдельного MCP-пакета и обещание «полноценный корпоративный 1С-продукт» имеют разные критерии.

## 1. Фактическая точка и решение

| Слой | Состояние | Доказательство / граница |
| --- | --- | --- |
| Исходник | `main`, HEAD `f98713a64c8c44a098497d222925ddd4d24215bb`, 124 записи в `git status --porcelain` на начало этапа | Большая пользовательская работа не зафиксирована; HEAD не является источником текущего VSIX |
| Локальный кандидат | `1c-bsl-ai-copilot-1.0.11.vsix`, SHA-256 `a95ea52a1d0ff9fa6dc85f8608df8cdf01de6ab8240977b2c26fe919b3a6ae3a` | `tests/release_qa.py` прошёл 2026-11-10 до изменений релизной документации/CI; пакет не содержит эти документы |
| IDE | Установленный 1.0.11: packaged smoke 4/4 и физический Tab 4/4 в VS Code и Cursor, контролируемый HTTPS с сохранёнными реальными ответами | [Отчёт](../tests/PACKAGED_INLINE_RELEASE_REPORT_2026-11-02.md); это не новая live inference проверка |

| Публичные каналы | GitHub показывает материалы до 1.0.3; Open VSX API на 2026-11-10 возвращал 1.0.3; Marketplace README ссылался на VSIX 1.0.7 | Версия Marketplace API не подтверждена; публичные карточки нельзя считать текущим кандидатом |

Решение: **готовить открытую бету без набора закрытой пилотной группы**. Полноценный Team GA/B2B остаётся отдельным выпуском. Платная широкая кампания о «готовом AI для всей 1С» сейчас не проходит доказательный порог. Если live NormaHub откладывается, допускается только тихий preview исходников/VSIX с явным статусом «AI-интеграция в этом пакете не переквалифицирована».

## 2. Последовательный путь к открытой бете

### R0. Зафиксировать объем и обещания

Поддерживаемый первый сценарий: разработчик BSL в VS Code/Cursor получает черновик запроса/объяснение, видит preview, сам проверяет и применяет. Локальные эвристики, шаблоны и MCP идут как вспомогательные инструменты, с явным `draft`/`unknown`. Inline — экспериментальная функция, пока не достигнут интерактивный p95; не обещать мгновенный Tab. Не обещать готовые `.cfe`/`.epf`, запуск Vanessa, TurboConf, все конфигурации 1С или доказанную бизнес-корректность.

### R1. Свести исходник и артефакт

1. Просмотреть все 124 изменённые/новые позиции, включая старый изменённый бинарный 1.0.3, `dist`, `docs`, `tests`, `.agents`, `.codex`. Для каждого файла принять решение: код выпуска, тест, документация, приватный/временный артефакт или история. Ничего не удалять автоматически.
2. Убедиться, что нет секретов и чужих данных в исходниках, Git history, VSIX, evidence, скриншотах и release notes. Токены, ранее показанные в переписке, считать скомпрометированными для внешнего размещения: перевыпустить до настройки CI; не помещать их в `publish.sh`, URL, argv или issue.
3. Согласовать версию. Сохранённый 1.0.11 не перезаписывать; если меняется упаковываемый контент после его проверки, повысить версию и собрать новый пакет из выбранного SHA. Разделить reviewed commit, tag, CI-built VSIX SHA, опубликованные версии и установленный runtime.
   - Текущий `npm audit` нашёл одну moderate advisory у build-time esbuild (`^0.20.0`); production-only audit не нашёл уязвимостей. Переход на обновлённый esbuild проводить отдельным reviewed изменением с повторной сборкой/QA, без `audit fix --force` на текущем dirty пакете.
   - Перед публичной бетой добавить явный beta-статус, актуальную версию, быстрый старт, поддержку и ограничения в **упаковываемые** README/CHANGELOG и карточки. Текущий VSIX 1.0.11 содержит README предыдущего среза; изменение README создаст новый пакет с новой версией, а не тихую замену файла 1.0.11.
4. Коммит/тег выполняются только после просмотра состава и решения владельца о выпуске. Тег `vX.Y.Z` должен совпадать с `package.json`; пуш тега создаёт только **draft prerelease**, не загружает пакет в реестры. Ручной `workflow_dispatch` по этому тегу с `promote=true` публикует draft VSIX в обе площадки и открывает GitHub prerelease. Отдельный `publish.sh --check` проверяет локальный пакет и tag без сетевых изменений.

### R2. Прогнать gates на точном пакете

| Gate | Критерий выхода | Сейчас |
| --- | --- | --- |
| Source/release hygiene | Чистый reviewed SHA/tag; совпадение версии и файлов пакета; checksum; отсутствие ключей/PII; известные лицензии зависимостей; не смешивать старый VSIX | Не закрыт: dirty worktree |
| CI/static/Core | `npm ci`, `npm test`, `pnpm build`, `pnpm lint`, `tests/release_qa.py`, package MCP positive/negative calls; на tag CI повторить | Локально ранее pass; после freeze повторить |
| Installed IDE | Новый профиль на поддерживаемых версиях VS Code/Cursor, RU/EN, panel/commands, выбор BSL, preview/apply/Undo, stale target, Tab/Escape, отказ при offline/401/429 | 1.0.11 частично подтверждён; точный финальный CI VSIX ещё не установлен |
| 1С выбранного объёма | На выделенной собственной базе: реальный запрос с параметрами, независимое expected, результат сравнения, неподдерживаемые случаи и очистка среды | 7/7 SELECT на учебной Linux; шире не заявлять |
| Live AI и деньги | Для открытой беты: новый canary через реальный gateway по каждой публично обещанной AI-дорожке, с ошибками, временем, токенами и стоимостью. До платного широкого продвижения: полный заранее зафиксированный корпус 30/30 и сверка model route по request IDs. Silent fallback запрещён | Не закрыт; 17/30 уникальных cases в прежнем прогоне |
| Privacy/support | Публично указаны data flow, что локально/что отправляется в облако, условия оплаты, контакт поддержки, минимальный порядок удаления/отзыва ключа и incident path | Нужна проверка актуальных условий NormaHub и канал владельца |

У «успешного HTTP 200», принятого Tab и полезного корректного результата разные знаменатели. В отчёте live обязательно сохранить все попытки, N, latency от UI до предложения, долю полезных результатов, cost/useful result и список отказов. p99 при малом N не использовать как публичную метрику. Если inline остаётся около 6 секунд, оставить его экспериментальным/по ручному вызову либо менять route/UX и проверять заново; не маскировать его результаты query-workflow. Canary разрешает ограниченное beta-позиционирование, но не доказывает качество на полном корпусе.

### R3. Подготовить поставку и поддержку

- Один installation page: VS Code Marketplace, Open VSX, GitHub Release/VSIX; одинаковые версия, SHA, release notes, минимальные IDE/OS требования. Проверить фактическую доступность в Cursor: Open VSX публикация не равна мгновенному появлению в его поиске.
- Один quick start за 3–5 минут: установить → открыть BSL → локальная проверка без ключа → подключить ключ при желании → запрос по описанию → preview/copy/apply → проверить в 1С. Демо использует собственную вымышленную схему и не обещает, что её объекты есть у клиента.
- На странице поддержки: issue template для бага с версией IDE/расширения/1С, воспроизведением и обезличенным логом; отдельный приватный канал для security/данных. Не просить присылать исходники, ключи и журналы с PII в публичный issue.
- Зафиксировать release owner, технического on-call, ответственного за стоимость gateway, rollback: снять проблемную карточку/пререлиз, остановить промо, выпустить patch с повышением версии; для серверного AI route — безопасный kill switch/лимит, без молчаливой подмены модели.
- До дня анонса сверить актуальную цену и условия NormaHub, проверить доступность API/баланса и поддержку. Не выводить credit как рубли без контракта.

### R4. Публикация и проверка после неё

1. Пуш reviewed source и tag; дождаться зелёного CI и draft GitHub Release. Проверить архив, checksum, содержимое release notes и ссылки на demo/support.
2. После настройки Marketplace Trusted Publishing policy для `normahubcc/1c-bsl-ai-copilot/.github/workflows/release.yml` и ротированного `OVSX_PAT` в GitHub Secrets запустить manual promotion на том же tag. Workflow использует GitHub OIDC для Marketplace и секрет только для Open VSX. [Microsoft объявила прекращение global PAT с 2026-12-01](https://code.visualstudio.com/api/working-with-extensions/publishing-extension); без policy публикация Marketplace не пройдёт.
3. Проверить версии в Marketplace/Open VSX через API, скачать опубликованные VSIX, сравнить идентичность package/version/содержимого; установить из каждого канала в чистый профиль. Не считать успешный upload завершением релиза.
4. Только после этого публиковать ссылки в медиа. Первые 48 часов ежедневно отслеживать установки, activation, первую применимую задачу, 401/429/timeout, расходы, обращения и отмены; при серьёзной ошибке остановить продвижение и выдать patch/известное ограничение.

## 3. Что нужно для полноценного 1С / B2B GA

Это отдельная программа, а не косметическое переименование беты. Возможность допускается к обещанию только после своего evidence:

1. **Польза и домен.** Выбрать узкий платный сценарий (например, query + review для определённых типов конфигураций), 80–120 заранее размеченных задач с независимым 1С oracle, позже 300–500 для Team GA. На закрытой выборке измерить корректность с первой попытки, после ограниченного repair, дефекты, полное время и цену полезного результата. Без набора пилотной группы это можно делать через независимых 1С-экспертов и обезличенный корпус; нельзя заявлять рыночную эффективность до реального использования.
2. **Исполнение 1С.** Отдельный безопасный runner и база под поддерживаемые версии платформы/конфигурации/СУБД; query, модули, движения, формы и Vanessa проверяются разными наборами. Разделить syntax, selected-query execution, full-module behavior и business approval. Учебная Linux база подтверждает только свой профиль. Для .cfe/.epf нужен фактически собранный артефакт, установка и сценарий работы. Для Конфигуратора Windows — отдельная программа CG1/CG2, не включать её в обещание VS Code релиза.
3. **Корпоративные границы.** Доверенный backend: identity/tenant isolation, серверные бюджеты и caps, роли и approvals, аудируемый отзыв доступа, retention/region/upstream data flow, проектные политики и отрицательные тесты. Один VSIX и MCP annotations этого не обеспечивают.
4. **Информационная безопасность.** Threat model для кода/метаданных/ТЖ, secret scanning, зависимости/SBOM, provenance пакета, независимый security review, изолированный runner, аварийный отзыв/rollback. Явные условия о правах на ИТС и чужой код; не индексировать закрытый корпус без прав.
5. **SLO и экономика.** Реальная p50/p95 e2e по разным профилям, ошибка/отмена/стоимость, подтверждённый billing; p95 inline ≤1,5 с — предложенная цель продукта, не текущее достижение. Нужны бюджетные лимиты, rate limit, поддержка, мониторинг и runbooks. Публичный SLA только после наблюдения.
6. **Совместимость и сопровождение.** Матрица Windows/Linux, IDE, платформа 1С, XML/EDT, BSL/OScript, конфигурации, single/multi-root; версия клиента/модели/runner pinned, migration/rollback, цикл security patch и support SLA. `unsupported` показывать явно.
7. **Коммерческая готовность.** Условия B2C/B2B, кто покупает и кто платит за токены/поддержку, договор и DPA при необходимости, корректные условия Инфостарта/каталогов, доступный канал поддержки и владелец инцидента. Для claim «лучше конкурента» — парный benchmark на актуальных версиях и одинаковых задачах, без переноса локального теста на весь рынок.

Исходные технические пороги и G0–G5: [AI/B2B план](AI_B2B_PRODUCT_TECHNICAL_PLAN.md#15-release-gates-и-definition-of-done). Решение «не набираем пилотную группу» снимает этот организационный шаг для открытой беты; для Team GA нужно другое честное доказательство повторной пользы и экономии в реальной работе.

## 6. Схема продвижения и измерения

**Сегменты.** S1: индивидуальный 1С-разработчик в VS Code/Cursor — быстрый запрос и preview. S2: руководитель небольшой 1С-команды — контролируемое применение, качество и стоимость. S3: корпоративный архитектор — только после G3–G5. Для S3 не продавать текущий VSIX как готовый tenant-isolated контур.

**Воронка:** просмотр карточки/статьи → переход на install → установка → открытие BSL → локальный первый результат → подключение ключа → первый полезный AI-черновик → самостоятельная проверка → повторное использование → платёж/командный запрос. Для каждого шага отдельно считать знаменатель и причины отказа. Канал определять UTM на собственных ссылках и агрегированными данными площадок; исходный код/промпты/PII не отправлять в маркетинговую аналитику. Метрика продукта — принятый полезный результат и полное время до него, не число генераций или загрузок.

**Бюджет и порядок:** первые 2 недели — только органические карточки, demo и ответы на вопросы; платные размещения после 30/30 live-eval и первых реальных сигналов повторного применения. Малые контролируемые тесты каналов сравнивать по cost per activated developer и cost per useful result, а не CPM. Если inline медленный или gateway нестабилен, остановить paid traffic и направить спрос на проверенный локальный/query workflow.

**Обратная связь без пилотной группы:** публичный issue template, обезличенный feedback form, еженедельная выборка добровольных кейсов, открытый changelog. Не маскировать это под репрезентативное исследование. Критичные баги и жалобы на расход денег получают отдельный канал и журнал инцидентов.

## 7. Масштабные дополнительные действия — после подтверждения спроса

1. **Экосистемный пакет для 1С-сообщества:** воспроизводимые open-source fixtures, benchmark задач запросов/BSL, независимая разметка специалистов, публичные fail cases. Это создаёт доверие и полезно даже без покупки; нельзя раскрывать чужой код/ИТС без прав.
2. **Образовательное партнёрство:** школы и курсы 1С, методические вебинары «AI-черновик и проверка в 1С», учебная база и задания с oracle. Мерить долю завершённых упражнений и повторное применение, а не выдавать курс за production evidence.
3. **Интеграторский канал:** 2–3 компании внедрения с отдельными условиями безопасности, install/update и бюджетов; paid enablement после backend tenant/policy gates. Это B2B distribution, а не обход отсутствующего isolation.
4. **Отдельный MCP product:** npm/другая подтверждённая поставка, versioned tool schemas, официальная Registry + Glama; целевая аудитория — внешние агенты. Не смешивать его funnel и качество с VSIX.
5. **Windows/Конфигуратор линия:** отдельный feasibility PoC, session/base binding, безопасный обмен, сборка/проверка в Windows, юридическая и UX приёмка. Массовое продвижение среди Конфигуратора только после CG2.
6. **Сравнительный открытый benchmark:** 30–50 парных задач против актуальных альтернатив при одинаковом времени/бюджете и независимом oracle; публиковать также проигрыши. Claim превосходства разрешать только в подтверждённом узком сегменте.

## 8. Решения владельца и стоп-факторы

Сейчас можно завершать локальную подготовку, исправлять pipeline и писать черновики без доступа к учётным записям. Для внешнего выпуска нужно решение CEO о **точной версии и позиционировании открытой беты**, просмотр огромного dirty diff перед коммитом, рабочие права GitHub/Marketplace/Open VSX, безопасно перевыпущенные публикационные токены, согласованные data flow/цена/support и разрешённый live NormaHub test budget. Если live test снова отложен — выпускать только quiet preview с соответствующей формулировкой. Коммит/тег, изменение карточек и размещение статей — отдельные внешние действия со следом выполнения; один этот документ их не совершает.
