# Реальные проверки запросов в учебной 1С

Корпус использует отдельную минимальную конфигурацию из `fixture/`, файловую базу и движок **учебной 1С 8.3.27.1508**. Все данные тестовые. Программа очищает документы и движения своей тестовой базы перед заполнением: **не загружайте её в существующую пользовательскую базу**.

`prepare.js` вызывает настоящее общее ядро продукта через JSON CLI, генерирует BSL без подмены алгоритмов и вставляет его в серверные функции тестовой конфигурации. Значения измерений здесь строки; это небольшой функциональный корпус, не проверка произвольной ERP-схемы или клиент-серверной производительности.

## Подготовка

После сборки расширения:

```bash
node tests/onec_engine/prepare.js /absolute/path/to/new-isolated-lab
```

Для проверки именно VSIX сначала извлеките пакет и укажите его CLI:

```bash
TOOLBOX_CLI=/absolute/path/to/extracted/extension/dist/toolbox-cli.js \
  node tests/onec_engine/prepare.js /absolute/path/to/new-isolated-lab
```

Скрипт отказывается перезаписывать существующий каталог `config`. Файлы конфигурации и входные запросы остаются в каталоге стенда для проверки. Установите официальную учебную платформу в отдельное окружение с графическим или виртуальным экраном. В проверенном Docker-стенде каталог стенда монтируется как `/lab`; доступные извне порты не нужны. Тестовый модуль пишет `/lab/query-results.txt` и завершает приложение.

## Запуск в окружении 1С

Точный путь бинарника зависит от установки. В использованном Linux-стенде:

```bash
/opt/1cv8t/x86_64/8.3.27.1508/1cv8t CREATEINFOBASE \
  'File="/lab/ib";Locale=ru_RU;' /DisableStartupDialogs /Out /lab/create.log

/opt/1cv8t/x86_64/8.3.27.1508/1cv8t DESIGNER /F /lab/ib \
  /LoadConfigFromFiles /lab/config /UpdateDBCfg /DisableStartupDialogs /Out /lab/load.log

/opt/1cv8t/x86_64/8.3.27.1508/1cv8t DESIGNER /F /lab/ib \
  /CheckConfig -Server -ThinClient /DisableStartupDialogs /Out /lab/check.log

/opt/1cv8t/x86_64/8.3.27.1508/1cv8t ENTERPRISE /F /lab/ib \
  /DisableStartupDialogs /DisableStartupMessages /Out /lab/enterprise.log
```

Проверяйте код выхода и лог каждого этапа до перехода к следующему. Загрузку и проверку конфигурации запускайте отдельными командами. В учебной версии допускается один сеанс базы; завершайте предыдущий перед новым запуском. Код выхода запуска приложения сам по себе не является доказательством исполнения: обязательны свежий файл результата, полный набор ожидаемых сценариев и отсутствие `FAIL`.

## Проверяемые результаты

Ожидается `PASS|seed` и 11 бизнес-проверок:

1. Достаточный остаток даёт пустую таблицу дефицита.
2. Требуется 12, доступно 10 → дефицит 2.
3. Две строки по 6 агрегируются в одну потребность 12.
4. Отсутствующий остаток даёт доступно 0, не теряет строку из-за NULL.
5. Остатки разных складов не смешиваются.
6. Явное сопоставление склада из шапки используется вместо склада строки.
7. Текущие несохранённые строки и сохранённый источник читаются согласно выбранному режиму.
8. Пустая табличная часть даёт пустой результат.
9. Период до прихода не видит будущего остатка.
10. Исходный SELECT и пакет после рефакторинга совпадают по числу строк, значениям, типам и NULL; используется правильный индекс результата пакета.
11. Граница момента документа с исключением собственных движений отличается от явно заданного периода после движения согласно контракту параметра.

Не проверяются конкурентные транзакции, клиент-серверные планы СУБД, полноценное проведение, произвольные конфигурации, перехваты .cfe, GUI формы и исполнение шагов Vanessa. Для них нужны отдельные профильные сценарии.

## Отдельная проверка typed comparator Core

Новый лабораторный срез не изменяет исходную fixture или старую базу. Подготовьте **несуществующий** новый каталог внутри собственного lab mount, собрав `pnpm build`:

```bash
node tests/onec_engine/prepare_verification.js /absolute/own-lab/new-verification /lab/new-verification
```

Скрипт создаёт собственную минимальную конфигурацию и две версии запроса: настоящий продуктовый генератор и контролируемую тестовую мутацию без агрегирования. Независимый ожидаемый результат задан заранее: 6 + 6 при остатке 10 → дефицит 2. Это отрицательный контроль harness, не найденный AI дефект и не полноценный поиск контрпримеров.

Создайте новую `/lab/new-verification/ib`, загрузите `/lab/new-verification/config`, выполните CheckConfig и Enterprise по отдельности, заменив пути в командах выше. Процессу Linux 1С нужны `LANG=ru_RU.UTF-8` и `LC_ALL=ru_RU.UTF-8` с установленной locale: иначе возможен отказ чтения кириллических XML-имён. Используйте собственный Xvfb/display согласно профилю. Не переносите команды на неизвестную существующую базу.

После успешных кодов выхода, логов и свежего `verification-results.txt`:

```bash
node tests/onec_engine/check_verification.js /absolute/own-lab/new-verification
```

Если файлы контейнера недоступны host-пользователю, прочитайте только свой result через разрешённый `docker exec ... cat` в новый host artifact и передайте его третьим аргументом checker. Не меняйте права соседних данных и не выдавайте агенту production-доступ. Проверяются runId, свежесть, source hashes и конкретные значения. Checker передаёт реальные выходы новому JSON CLI, сохраняет отчёт с `authenticatedCorporateRunner=false` и не выдаёт caller comparison за авторизованный receipt. Подробности: [VERIFICATION_CORE.md](../../docs/VERIFICATION_CORE.md).
